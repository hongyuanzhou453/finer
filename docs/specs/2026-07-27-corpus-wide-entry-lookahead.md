# 全语料入场前视偏差 — 根因与影响（2026-07-27）

> **状态：已发现，未修复。修复范围超出既有授权，等用户决策。**
> 触发：国际股回写脚本执行前的对抗审查（脚本已写好但**未执行**，data/ 未被改动）。

## 1. 结论

**语料里 50.4%（1,669/3,313）的 action 在其研报日期之前入场。** 这不是国际股问题，
受影响的绝大多数是美股。若按正确规则修复，**2,241 条已结算里有 1,027 条（45.8%）
的入场 bar 会后移**——接近一半的记分卡基础会变。

## 2. 根因：date-only 时间戳被当成时刻使用

F1/F2 上游只拿到研报的**日期**，没有发布时刻。`published_at` 因此被填成
「当地零点」——实测 3,229/3,313（97.5%）的 `intent_published_at` 换算到北京时区
恰为 `00:00`（其余 84 条是真实带时刻的 KOL 内容）。

北京时 D 日零点 ≡ **UTC D−1 16:00** ≡ **纽约时 D−1 11:00/12:00**。
`MarketCalendarTimingPolicy` 把它当作一个真实时刻解释，于是判定「D−1 美股盘中」→
`action_executable_at` 落在 **D−1**，比研报日期早一整天。

```
研报日期 2025-12-16
  published_at  = 2025-12-16T00:00:00+08:00   ← 只有日期，零点是占位
  纽约本地       = 2025-12-15T11:00:00-05:00   ← 盘中
  action_executable_at = 2025-12-15T11:05:00-05:00
  实际入场 bar   = 2025-12-15                  ← 研报发布前一天
```

同一机制对**任何位于北京以西的市场**都成立（美洲、欧洲）；亚太市场因为零点仍在
当地同日盘前，反而是对的。

## 3. 与前一份评估的关系（含自我更正）

`2026-07-25-intl-calendar-impact-assessment.md` 把问题定义成「国际股挂错日历」，
量到 870 条错标、237 条入场 bar 会移。那份评估的**测量是对的，归因是错的**：

- ❌ 原叙事「纽约时间上午发布的日股研报、东京已收盘」——**数据里不存在这个发布时刻**。
  存量中的 NY 11:00/12:00 本身就是北京零点的渲染（668 条 `11:00-05:00` + 197 条
  `12:00-04:00`，都恰好等于 16:00 UTC）。
- ✅ 「237 条入场 bar 会后移」在「只改市场标记」这个前提下成立。
- ⚠️ 但只改市场标记是**不够且有害的**：审查实测，修完之后仍有 **234 条**欧美标的
  入场早于研报日，而它们会被判为 `entry_bar_moves=False` → 保留旧结果并被盖章
  「同 bar、无需重算」。等于把「错日历的前视」换成「对日历的前视」并认证为已修。

## 4. 影响量化（按正确规则重算）

规则 = 真实市场（ticker 归一化）+ **地板约束**：date-only 的 published_at
不得产出早于研报日的可执行时刻。

| 指标 | 数值 |
|---|---|
| date-only published_at | 3,229 / 3,313（97.5%） |
| 当前入场早于研报日 | **1,669**（全部挂在 stamped market=US 下） |
| 需要地板修正 | 1,299 |
| 已结算中入场 bar 必然后移 | **1,027 / 2,241（45.8%）** |

后移条数按真实市场：US 669、JP 88、TW 45、UK 43、FR 42、AU 28、KR 27、CN 13、
NL 11、DE 7、BE 7、NO 6……

## 5. 为什么这会改变结论

前一份评估得出「look-ahead 未实质抬高业绩（胜率、中位数几乎不变）」——那个结论
是在 **237 条**的国际子集上得到的。现在受影响的是 **1,027 条、含 669 条美股**，
即记分卡的主体。1 天的前视对单条影响小，但当它系统性地作用在半个语料上时，
所有跨组比较（券商榜、市场榜、胜率 vs 均值）都建立在同一个偏移之上，
**必须重新测量后才能判断影响方向与幅度**，不能沿用 237 条上的结论外推。

## 6. 待决策

修复范围从「870 回写 + 237 重结算」变成「全语料时钟重算 + ~1,027 条重结算」，
**超出既有授权**，故停在此处。可选路径：

| 方案 | 内容 | 代价 |
|---|---|---|
| A. 全量修正 | 时钟地板约束进 `timing_builder`（前向）+ 全语料回写 + 1,027 条重结算 + 记分卡 v6 | 记分卡三代可比性断裂，需标口径版本；耗时最长 |
| B. 只修前向 | 只改 `timing_builder`，存量不动，新 action 起正确 | 存量记分卡继续带 50% 前视，且新旧口径混在一张榜上（更差） |
| C. 先量后决 | 先在**副本**上跑完整修复并出 v6 记分卡，与 v5 逐项 diff，看清影响再决定是否落盘 | 多一轮计算，但决策有据；**推荐** |

另：审查同时发现 4 项脚本层缺陷（审计文件在写入后才落盘、无并发写保护、
rebuild 一行命令忽略 `--data-root`、审计字段不足以脱离备份重建），
无论选哪条路径都需先修。

## 7. 未受影响的结论

审查逐条验证并确认干净的部分：入场 bar 判据的数学（`new > B_old ⟹ 换 bar`，
`new ∈ [old, B_old] ⟹ 同 bar`）成立且实测分区严丝合缝（0 越界）；237 条中
neutral / review_required / 手工语义 **均为 0**，不存在「清空后永久失结算」的风险；
`backtest_result=None` 可干净回环 Pydantic；`by_id` 定位无重复 id 冲突。
这些结论在扩大范围后依然适用。
